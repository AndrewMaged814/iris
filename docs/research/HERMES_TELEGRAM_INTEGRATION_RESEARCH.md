# Native Hermes Telegram integration

Research date: 2026-09-28. Read-only inspection over `ssh hermes` of `~/.hermes/hermes-agent`; installed checkout HEAD is `c1488ac947c9bc33fd65ec464548dc9d8edd6122` (the deployed v0.21.3 baseline). Inspected source files have no Git modifications. Findings are tied to this commit, not a guarantee about all Hermes releases. No bot messages, credentials, user records, source changes, or gateway restarts were performed.

## Smallest integration

Ship an ordinary enabled Iris plugin containing typed store tools and a native Telegram handler factory. Keep Hermes' Telegram transport, message/session processing, agent loop and replies. Use a separate Iris bot/profile, rather than routing multiple products through one shared bot. The plugin contacts the existing Shopify connection service; it never receives Shopify access/refresh tokens in model-visible results.

`register(ctx)` may call `ctx.register_telegram_handler(factory)` (alias of `register_platform_handler('telegram', factory)`) and `ctx.register_tool(name, toolset, schema, handler, ..., is_async=False)`. Factory signature is `(application, adapter)`; SDK imports belong inside it. Capture the profile home at registration rather than resolving a later callback's ambient process profile. The plugin manager and tool registry are home-scoped; managers are cached by resolved Hermes home. [Plugin API](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/hermes_cli/plugins.py#L843), [scoped loader](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/hermes_cli/plugins_loader.py#L265)

Secondary multiplex profiles discover plugins and connect adapters inside their profile runtime scope. They also get a profile-owned authorization closure, owner stamp and separate bot credential claim. This makes the factory available to that profile's adapter. It does **not** mean arbitrary PTB callbacks automatically execute inside a Hermes agent-session ContextVar scope. For a shared primary bot with `gateway.profile_routes`, transport authorization and routed runtime profile differ; this slice should avoid that arrangement. [Multiplex adapter ownership and connect](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/gateway/run_adapters.py#L1014)

## Confirmation handler

Register a tightly scoped `CallbackQueryHandler(on_confirm, pattern=r'^iris:confirm:')` and, if needed, a specific PTB `CommandHandler('confirm_store', on_confirm_command)` using the factory's `application.add_handler(..., group=0)`. Plugin factories run before core handlers; PTB selects the first matching handler per group. Avoid another callback catch-all. Preserve core `/start`, photo intake, approval/model-picker buttons and unknown-command processing. [Native factory contract/example](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/website/docs/developer-guide/plugins/index.md#L1337)

Before accessing confirmation state, call the adapter's `_is_callback_user_authorized(str(actual_user.id), chat_id=str(actual_chat.id), chat_type='private', thread_id=None)` and deny on exception. It prefers the injected full runner authorization closure and supports multiplex profile closures; fallback denies absent allowlist unless explicitly allow-all. This authorizes participation, not ownership of a particular merchant connection. [Adapter authorization](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/plugins/platforms/telegram/adapter.py#L803)

Read actor and chat IDs only from Telegram's actual `Update`; require private chat. An opaque button payload/command argument identifies a pending connection, never its owner. The backend must compare it against recorded initiating user/chat/profile, pending expiry, verified shop and unused state; consume once atomically. Reject a forwarded button, another allowed user, wrong chat/profile, stale state and duplicate tap. Only then activate. This is Iris-owned policy; native gateway access authorization alone cannot establish connection ownership.

The simpler `ctx.register_command('confirm-store', handler)` handler receives only `raw_args`. In this revision plugin command dispatch occurs before `_set_session_env` for an agent turn; `_handle_message` resets prior session vars at entry. Do not use `get_session_env` to recover authenticated actor identity in such a command. A PTB handler with native Update context is preferable here. [Early plugin-command dispatch](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/gateway/run_inbound.py#L1027)

## Trusted tool identity

For `store_connection` status/begin and `store_products`, derive identity from `gateway.session_context.get_session_env`, not model arguments. Check `HERMES_SESSION_PLATFORM == 'telegram'`, private chat type, nonempty actual user/chat/session key, and the plugin's captured profile-home context. The schemas must not accept actor IDs, shop selector overrides, credentials, connection activation, arbitrary GraphQL, or arbitrary service routes. The service selects the active connection using trusted binding identity.

`get_session_env` prefers a task-local ContextVar, including explicitly empty values; never-bound values fall back to `os.environ`. `session_context_engaged()` is a process-level latch, **not** proof that this task currently has a valid Telegram identity. Reject missing fields even if the latch is true. Native callbacks need Update-derived identity, while agent tools may use the bound context. [Session context](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/gateway/session_context.py)

The runner binds `HERMES_SESSION_PROFILE` from `source.profile or ''`. Empty is therefore a legitimate standalone/default profile value. Accept it only when the captured home establishes the intended configured profile; never treat empty as permission to use another home. Named multiplex sessions should match the named profile. Concurrent owner tests must confirm ContextVars and executor propagation keep tool identity separate. [Runner context binding](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/gateway/run.py#L4219)

## Native capability restriction

`platform_toolsets.telegram` is real capability selection. Use an explicit YAML list with `iris-domain`, `web`, `vision`, and read-only skill access. Built-in `skills` contains `skills_list`, `skill_view` **and `skill_manage`**. There is no first-class per-tool `disabled_tools` configuration found in this pinned implementation; plain individual tool names are not supported toolset names. [Built-in membership](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/toolsets.py#L101), [selection semantics](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/model_tools.py#L280)

A native alternative to a custom policy hook is `toolsets.create_custom_toolset('iris-skill-read', description, tools=['skills_list', 'skill_view'])`, then select that set in place of `skills`. Explicit custom toolsets pass through platform resolution. This helper mutates process-global `TOOLSETS`, so keep its fixed name/membership consistent across profiles. Do not disable the entire `skills` set globally: subtraction would also remove the two reads from the custom set. Verify effective schemas on the actual deployed plugin. [Custom toolset helper](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/toolsets.py#L444), [native test](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/tests/tools/test_toolsets.py#L178)

Read-only synthetic execution using the installed Hermes Python verified `_get_platform_tools` plus `resolve_toolset` for `[web, vision, iris-skill-read, no_mcp]`: selected sets were exactly `iris-skill-read`, `vision`, `web`; resolved names were `skill_view`, `skills_list`, `vision_analyze`, `web_extract`, `web_search`. The assertion that `skill_manage` was absent passed. Plugin/MCP key discovery was mocked empty and no live profile config was changed; this proves the helper/selection path, not the final deployed schema catalog.

Explicit lists have compatibility additions: newly discovered plugin toolsets absent from `known_plugin_toolsets.telegram` can auto-enable; newly shipped built-ins can also be added absent declined-state records. Enabled MCP servers may be merged unless the list includes `no_mcp`. Record known plugin/built-in choices, exclude broad composite defaults, set native `agent.disabled_toolsets` for unwanted groups, and inspect final individual schemas. Use `no_mcp` while none are intended. [Platform resolution, plugin additions and MCP merge](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/hermes_cli/tools_config.py#L535)

Keep `terminal`, `file`, `code_execution`, browser control, delegation, cron, arbitrary outbound sending and generic connector management out of the merchant profile. Neither SOUL nor a "read only" sentence prevents tool use. A native `pre_tool_call` hook can block specific calls, but exceptions are logged and dispatch continues, so it is insufficient as the sole secret boundary. Prefer native selected schemas plus a service which only exposes owner-scoped typed reads. [Pre-dispatch hook failure behavior](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/model_tools.py#L761)

Credential protection ultimately belongs to process/storage permissions and the service response contract. Hermes plugins are trusted Python, not a sandbox. Keep Shopify tokens, refresh credentials and encryption keys in the auth service's private storage, outside skills, prompt-visible docs and Hermes media directories; return only status/shop identity and product data. A same-user service/agent deployment does not constitute strong OS isolation from a malicious plugin. `skill_view` has directory/path checks, but those are not permission to place secrets inside skill support files. [Skill file serving checks](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/tools/skills_tool_plugin.py#L69)

## Packaging

Use `plugins/iris-domain/plugin.yaml` and `__init__.py` exporting `register(ctx)`. Declare name/version, `requires_hermes`, and provided tool/hook metadata; directory basename supplies registry key. Profile user plugins are discovered under `$HERMES_HOME/plugins`; project `.hermes/plugins` discovery is opt-in. Standalone user plugins require `plugins.enabled: [iris-domain]`; `plugins.disabled` wins. Manifest declarations do not grant arbitrary capabilities. [Manifest model](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/hermes_cli/plugins_manifest.py#L323), [discovery and enable gates](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/hermes_cli/plugins_discovery.py#L149)

`hermes profile install` copies distribution payload and bootstraps profile directories. With Iris' explicit `distribution_owned`, include the plugin directory and needed nonsecret files there. There is no manifest plugin-dependency installer/post-install execution: copying Python source does not install dependencies or start Shopify/Hermes services. Config on normal distribution update is preserved, so adding `plugins.enabled` or restricted toolsets upstream requires an explicit operator config migration. Never ship runtime credentials/state. [Distribution installation/update implementation](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/hermes_cli/profile_distribution.py#L444)

## Version gap and minimum verification

The pinned Telegram initial connection wires plugin factories, but a failed `Application.initialize()` attempt rebuilds the application and registers only core handlers. The retry path omits plugin factories. Full adapter reconnect calls `connect` again, but that does not repair a rebuilt application which already succeeded and stayed connected. This is a concrete reliability gap to reproduce or resolve in a supported Hermes revision, not a reason to build another poller. Do not patch host source silently. [Retry rebuild](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/plugins/platforms/telegram/adapter.py#L2920)

Before claiming readiness, perform these checks with synthetic records and a separate test bot:

1. Install the packaged plugin into the target profile; inspect `hermes -p iris-production plugins list` and `hermes -p iris-production tools --summary`. Confirm enabled plugin and exact effective tool schemas, not only configured names.
2. Use a fake PTB app/native adapter factory test to assert the scoped callback and exact command register before core; test gate denial/exception, wrong user/chat/profile, expiry, replay and competing allowed users. Exercise callback ownership against the real service boundary.
3. Run native ContextVar tests for two concurrent owners, empty standalone profile and named multiplex profile. Domain tools must deny CLI/no-context and ignore forged identity arguments.
4. Reproduce the initial network-failure/rebuild path and verify plugin handlers remain present; keep readiness false if this revision loses them. Upstream factory tests only prove registration APIs and invocation, not this retry path. [Existing factory tests](https://github.com/NousResearch/hermes-agent/blob/c1488ac947c9bc33fd65ec464548dc9d8edd6122/tests/gateway/test_platform_plugin_handlers.py)
5. In the live authorized test chat, complete browser OAuth, original-user confirmation, product read, `/new` and restart recovery. Check core buttons/photo intake still work and no token/secret appears in prompts, outputs or logs. Keep the remaining investigation-case flow explicitly unimplemented until its own proof passes.

No successful live onboarding, safe restricted runtime, or retry-path repair was established by this research.
